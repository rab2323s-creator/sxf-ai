DEFINITION

What is vibe coding?

Vibe coding is a way of creating software by asking an AI system to generate code in natural language and then changing the result through further prompts. Andrej Karpathy popularized the term in February 2025. The original phrasing described accepting generated code without closely reading it. That informal approach may speed up experiments but is not sufficient for production.

Example: a founder requests a cost calculator. The AI produces a page. The founder notices that a negative number results in a nonsensical bill and asks for a correction. The next version looks better, but only an independently calculated expected output and automated tests establish whether it is right.

A useful distinction: prompting is how the implementation begins; testing and review decide whether it is safe and correct. Vibe coding is not a programming language, a single product, or a guarantee that non-programmers can safely maintain complex applications.

PRACTICAL WORKFLOW

How to vibe code a website in seven steps

  1. Define a narrow outcome: for example, a static API cost calculator with five numeric fields.
  2. Specify acceptance tests first: correct formula, invalid inputs, zero requests, mobile labels, and accessible errors.
  3. Choose a controlled environment: a disposable sandbox and a version-controlled repository when possible.
  4. Generate one working slice: form plus calculation, without accounts, payments, third-party trackers or unnecessary packages.
  5. Inspect what changed: check the code diff, dependencies, outbound requests and any privilege escalation.
  6. Run independent tests: expected values computed by hand; invalid, extreme and adversarial input.
  7. Publish only after human approval: check accessibility, security, performance, recovery and ongoing ownership.

Copyable build prompt

Build an accessible static API token cost calculator.
Inputs: requests, input/output tokens per request,
input/output USD prices per million tokens.
Use plain HTML, CSS and JavaScript without dependencies.
No network requests, API keys, or unsafe HTML injection.
Reject negative, invalid or non-finite inputs.
Add unit tests for zero, ordinary, decimal-rate,
negative, malformed and overflow cases.
Show the formula and explain assumptions.
Do not claim tests passed unless you ran them.

Follow up with: “Show every changed file, run the tests, give exact outputs and identify limitations.” Do not accept “done” without inspecting test logs.

We built, broke, fixed and retested a working Vibe Coding app

We worked from a single, concrete build specification: five fields for request counts, input and output token volume, and per-million-token prices; all arithmetic runs locally, without network requests or external packages. We created a standalone SXF Cost Studio, a responsive website demonstrating the complete workflow: specify, implement, write a failing test, fix and verify.

Experiment method: An SXF-authored prompt-driven engineering exercise, with a runnable mini-app and automated checks. Measurements below come from local Node.js v22.16.0 and Chromium runs, not a paid agent-provider benchmark. Estimated API cost refers to the sample workload, not the price paid to develop this app.

1. Exact build prompt

Build an accessible static API token-cost estimator.
Use five nonnegative numeric inputs: requests, input tokens
per request, output tokens per request, and the two
USD prices per million tokens. Reject missing or invalid
values. Show an independently verifiable calculation.
No secrets, dependencies, network requests or tracking.
Support small-screen layouts and keyboard operation.
Add deterministic tests for normal and adversarial input.

2. First implementation and a reproducible failure

The initial implementation converted every input with Number(value). That meant an empty string silently became zero (Number("") === 0). An isolated regression check asserted that an empty request count must throw an error. The first run failed:

FAIL — missing expected exception (RangeError):
An empty request count must not silently become zero
Node.js v22.16.0; exit code: 1

Instead of masking the result with UI validation alone, we fixed the calculation boundary: reject blank strings, null, booleans, arrays and objects before numeric conversion, then enforce finite, nonnegative values and safe integer token counts.

TOTAL COST OF OWNERSHIP

How much does vibe coding cost?

Separate the builder subscription from AI inference charges, hosting and integrations, and human review and maintenance. Some services bundle usage while others sell credits, seats or API tokens. Double-counting included model calls exaggerates estimates; ignoring retries, deployment and review understates them.

A simplified token-budget equation is:

requests × (input_tokens × input_rate +
            output_tokens × output_rate) / 1,000,000

The lab above makes those assumptions transparent, but it is not a live pricing feed and deliberately omits caching and tool charges. The more useful economic metric is cost per accepted, verified outcome, not cost per prompt. See the SXF API pricing directory and the vendors' official plan documentation.

PRODUCTION SAFETY

Security and quality checklist

Working demos can conceal insecure authentication, secrets in frontend JavaScript, vulnerable packages, unvalidated inputs and excessive agent permissions. The OWASP prompt-injection guidance covers malicious instructions in untrusted content; GitHub recommends reviewing Copilot-generated pull requests as carefully as human work.

  • Keep API keys, credentials and admin controls outside public clients.
  • Enforce authorization on servers, not only in the visual interface.
  • Validate inputs and encode untrusted output; avoid unsanitized innerHTML.
  • Review package dependencies, versions, licenses and security advisories.
  • Use least-privilege tool access and human approval for spending and deployment.
  • Run unit, integration and browser tests; include negative and permission-denied cases.
  • Test mobile usability, labels, keyboard navigation and readable error messages.
  • Add backups, alerting, usage limits, rollback and change ownership before a production launch.

WHAT GOES WRONG

Common vibe coding mistakes

  1. Publishing the first visually attractive build without an acceptance test.
  2. Letting an agent modify production databases with broad credentials.
  3. Assuming a plausible explanation is evidence the code passed tests.
  4. Requesting too many features before validating the simplest user journey.
  5. Forgetting usage caps, storage charges and ongoing support.
  6. Failing to verify behavior on small screens and with keyboard navigation.
  7. Choosing a tool solely because of a model name rather than repository control and team workflow.

SEARCH INTENT

Frequently asked questions

What is vibe coding?

Vibe coding uses natural-language instructions to build and iteratively refine software with an AI coding tool. Review and tests are still needed before launch.

Is vibe coding the same as agentic coding?

No. Vibe coding is a human workflow style; agentic coding refers to an agent that can plan, change files and use tools. They can overlap.

Can beginners vibe code?

Yes for prototypes, but understanding HTML, JavaScript, Git and basic security makes production work substantially safer.

Is vibe coding free?

Some products offer free plans or trials. Real cost includes credit or token charges, hosting, integrations, testing and maintenance.

Can vibe-coded apps be production ready?

Yes if they pass appropriate security, permissions, accessibility, performance and acceptance tests, and an accountable human reviews changes.

Which vibe coding tool is best?

Use hosted builders for fast demo creation and IDE or CLI agents for repo ownership, test execution and code review. There is no universal winner.

Do I need to know programming?

Not for the first demo; debugging, data protection and deployment benefit greatly from programming literacy.

What are the main risks?

Broken behavior, unreviewed dependencies, unsafe data access, secrets exposure, prompt injection and unexpected usage bills.

How do I test AI-generated code?

Write expected outputs independently, run unit and browser tests, test invalid input, inspect diffs, audit dependencies and restrict permissions.

EMPIRICAL EVIDENCE

Does AI coding really make developers faster?

Productivity effects depend heavily on experience, workflow and task. In a 2025 randomized controlled trial involving experienced open-source developers working in familiar repositories, METR observed developers taking longer with AI coding tools despite expectations of speedup. This is one context, not a universal finding. Meanwhile, controlled research and field studies of code-assistance workflows have sometimes shown substantial gains on narrower tasks. Both findings are consistent with a practical lesson: benchmark your own workflow against quality-adjusted completion time and measure review and debugging, rather than assuming every generated line saves time.

Security evidence also supports explicit release gates. OWASP's 2025 LLM risk guidance identifies prompt-injection attack paths when agentic systems ingest untrusted instructions, while the NIST Secure Software Development Framework emphasizes design, verification and vulnerability response across the lifecycle.

METR: randomized study of experienced developers and AI tools ↗Peng et al.: experimental research on GitHub Copilot developer productivity ↗NIST Secure Software Development Framework ↗

These studies examine different populations and tasks; comparisons should not collapse their results into a single “AI productivity” percentage.
