DIRECT ANSWER

How do you deploy an AI agent in production?

Deploy the agent as a versioned, permissioned workflow — not a long HTTP request. Put an authenticated API in front, persist task and session state, dispatch work through a durable queue or workflow engine, apply bounded concurrency and idempotent tool effects, and measure independently accepted results. Test crash recovery and rollback before routing real traffic.

A hosted model or agent SDK alone does not supply all these production guarantees. Choose a managed agent platform, serverless API plus worker queue, or custom container fleet according to the work's duration, data requirements and operational constraints.

FIELD GUIDE

Prototype vs production: the contract changes

An agent that solves one prompt on a laptop is not yet a production service. Production AI agent deployment means that separate users can submit tasks safely, an interrupted execution can resume or reach a well-defined terminal state, and operators can explain every real-world action. The shift is from “did the model respond?” to “did the intended outcome happen, exactly within the permitted boundary?”

The six contracts that turn an AI agent prototype into a production system
Prototype questionProduction answer / evidence
Can it complete a task?Define an accepted outcome and verify the downstream state, not only the final message.
Does it remember the session?Use a durable session and workflow store; test resumed and expired sessions.
What if the provider times out?Apply bounded retries, backoff, budget caps and explicit unknown-outcome handling.
What if it sends twice?Create a stable business operation key; prove deduplication at the effect boundary.
Who can approve a refund?Enforce typed permissions and approval independently of the model's text.
What if a deployment goes wrong?Pin artifact and prompt versions, canary, observe and roll back deterministically.

REFERENCE ARCHITECTURE

A production AI agent architecture that survives the first outage

The safest default is an asynchronous boundary between accepting a task and carrying out long-running actions. Short queries can sometimes be served synchronously, but a workflow that calls multiple tools, waits for approval or must recover from failure needs persisted state and a separate worker lifecycle.

  1. Entry API: authenticate callers, authorize tenant and action, validate schema, assign immutable task_id and a request idempotency key.
  2. Durable enqueue: persist the task and queue intent atomically where feasible (for example, an outbox pattern); return 202 Accepted with a status URL for asynchronous jobs.
  3. Worker lease: claim a task for a bounded time, apply a global and per-tenant concurrency budget and record the execution version.
  4. Reasoning loop: run the chosen model inside application-owned time, tool and spend budgets; do not let the model assign its own authority.
  5. Tool gateway: validate typed inputs, enforce approvals and send stable operation keys to compatible external services.
  6. Commit and notify: save verified business state and final output; expose an audit trail, terminal status and controlled callbacks.

Design invariant: a user-visible completion status must not precede confirmation of the corresponding business effect. When a remote tool succeeds but its acknowledgement is lost, the system should mark the outcome unknown / reconciling rather than blindly executing the action again.

FIELD GUIDE

Persistent state, memory and long-running jobs

Store at least three distinct categories: workflow state (status, steps, attempt, lease and checkpoints), conversation/context state (permitted context and memory), and business state (the external effect you are responsible for). They have different retention periods and consistency requirements.

Which state must survive an AI agent worker restart?
Data / stateSource of truthMinimum recovery behavior
Task and workflow statusDurable DB / workflow historySurvives pod termination and client disconnect; step transition audit trail.
Conversation and retrieval contextSession store / controlled retrieval indexVersioned retrieval, tenant isolation, privacy retention and safe rehydration.
Side-effect ledgerBusiness DB or external provider operation recordStable operation key, idempotency window and reconciliation when acknowledgement is lost.
Execution versionImmutable deployment manifestRecords code/prompt/model/tool versions responsible for each run.
Approval receiptImmutable audit event with policy evidenceWho approved which exact action, scope, parameters and expiration.
DiagnosticsRedacted spans, metrics and structured event logsCorrelation by task ID without exposing secrets or full prompts by default.

Durable workflow products such as Temporal reconstruct execution state from persisted event history [8]. That improves recoverability, but durable execution is not the same thing as exactly-once external effects. Any network call after a checkpoint can still need target-side idempotency and reconciliation. For the long-term memory design layer, see AI Agent Memory.

SCALING & ADMISSION

Queues, scaling and rate limits: scale accepted work, not just pods

The backlog is where burst absorption becomes measurable. A queue can protect the web API from long tasks, but it can also hide a capacity crisis unless you observe the oldest job age, retry load, dead-letter counts and time to an accepted outcome. Do not scale solely on CPU: agent tasks are often I/O bound on models and external APIs.

As a rough capacity planning identity, average concurrency is arrival rate × mean time in the system (Little's Law under stable conditions); it is not a safe production cap by itself. Use p95/p99 task durations, memory footprint, runtime budgets and rate-limit tests to set an initial bound. Some tasks must stop at the tool boundary, no matter how many worker pods you create. FIELD GUIDE

Retries, idempotency and the unknown-outcome trap

At-least-once delivery is normal in many queue and retry systems. Replaying a model call is often only a cost issue; replaying send_email, create_refund or transfer_funds can be a real-world harm. AWS explicitly documents that replay can execute a side-effectful step again [3, 4].

Operational invariantSame business intent + same operation key → at most one committed intended effect, or an explicit reconciliation state.

Construct an idempotency key from stable business identity, such as tenant_id + order_id + refund_version, not from a random retry attempt ID. Enforce uniqueness transactionally where the effect and ledger share a database. For remote effects, use the external service's documented idempotency guarantee and query its state after an ambiguous timeout. A local “already called” flag is not proof that the remote operation succeeded.

REQUEST  → validate permission → durable task + operation_key
WORKER   → if completed: return recorded result
         → if external status unknown: reconcile first
         → else call tool with operation_key (when supported)
         → verify downstream state → record completion
TIMEOUT  → bounded backoff + jitter, then retry/reconcile
EXHAUST  → dead-letter / human review; never claim success

Important nuance: AWS describes an “exactly-once” execution model for some Step Functions Standard workflow tasks, with explicit retry qualifications [5]. That statement must not be generalized into an end-to-end guarantee for every remote side effect. An agent architecture should be precise about which boundary provides which guarantee.

For each of 120 unique task-N:send-confirmation keys, our test delivered the action three times: once in pass 1, again in pass 2, and again after the simulated restart. The naive implementation wrote each delivery. The RAM approach kept a set but lost it across the restart. The SQLite approach used a unique ledger key and inserted the local effect in the same database transaction. The test contains assertions for all expected counts.

RELEASE ENGINEERING

Step-by-step deployment and safe rollout

  1. Specify the outcome: pick one narrow workflow and define acceptance criteria, tool permissions, budget cap and a failure-state taxonomy.
  2. Package and version: commit application source, tests, dependency lockfile, prompt templates and tool schemas; build an immutable container or platform artifact.
  3. Prepare infrastructure: isolated staging environment, secrets manager, database, queue, worker identity, tracing and per-tenant restrictions.
  4. Make state recoverable: implement persisted checkpoints or workflow history, visibility timeouts/leases, idempotency keys, reconciliation and dead-letter handling.
  5. Test before traffic: run evaluation fixtures, duplicate deliveries, worker kill/restart, tool timeout, approval rejection, schema migration and cost budget tests.
  6. Canary the version: move a small, pre-defined share of eligible traffic to the release; compare outcome, tail latency, cost, safety events and support escalation against baseline.
  7. Roll back safely: shift new task intake back to the prior version and explicitly decide what happens to in-flight jobs, schema changes and pending approvals.
  8. Close the loop: write a release record with artifact ID, model/prompt version, observed metrics, on-call owner and review date.

Do not assume a “rollback” can undo an external action such as sending a customer email. Design reversible and irreversible steps separately; irreversible actions may require compensation, escalation or a human decision.

SECURITY & GOVERNANCE

Security, authorization and human approval belong outside the model

The model may suggest an action; the policy service decides whether it can execute. Give each workload a scoped identity, restrict network egress, isolate tenants, pin allowed tools and apply maximum transaction limits. Audit an approval against the exact operation payload, not an abstract blanket instruction. Sanitize logs and never store secrets in task context.

Observability, SLOs and incident response

Observe more than the provider response code. Attach the same task_id and trace ID to API admission, model calls, tool requests, checkpoints, approvals, retries and final verified outcomes. OpenTelemetry has evolving GenAI agent span conventions; treat unstable conventions as versioned interfaces [9].

FIELD GUIDE

Disaster recovery, data residency and exit strategy

Define RPO (how much verified workflow data can be lost) and RTO (how long the service may be unavailable). Map dependencies beyond the agent host: model endpoints, queues, database, vector retrieval, object storage, IAM and tool APIs. Store infrastructure and agent definitions as code, practice restore drills, and document data residency and retention obligations before procurement.

In a region-level outage, simply launching a second container is insufficient if all workflow state and secrets remain in the failed region. Microsoft describes disaster-recovery planning for agent services as explicitly involving the agent definitions and stateful dependencies [7]. Choose recovery architecture based on business requirements; avoid publishing an untested “multi-region ready” claim.

Exit contract for vendors: can you export prompts, run state, audit trail, dataset snapshots and versioned tool definitions in usable formats? Can your workers continue elsewhere without silently changing the approved authority model?

FIELD GUIDE

Seven deployment mistakes that create expensive incidents

  1. Using a web request as a durable job: a timeout can interrupt work after the API has already returned to a user.
  2. Assuming retries equal reliability: an unguarded retry can multiply irreversible tool actions.
  3. Storing task truth in worker RAM: autoscaling and restarts lose the very state needed for recovery.
  4. Scaling agent pods without controlling provider quota: additional concurrency increases 429s and costs.
  5. Allowing the model to approve itself: permission checks belong to external deterministic controls.
  6. Celebrating a green trace instead of a verified outcome: the tool can return 200 while the business state remains incorrect.
  7. Rolling back code without handling in-flight workflows: old and new workers may interpret schema or checkpoints differently.

For a focused quantitative approach to repeated failures, see AI Agent Reliability: 12 Metrics. For operational traces, see AI Agent Observability.

FIELD GUIDE

Frequently asked questions about deploying AI agents

How do you deploy an AI agent in production?

Package the agent as a versioned runtime, add a durable task queue and persistent state, bind tools to least-privilege identities, define retries and idempotency for side effects, instrument outcomes and run a staged release with rollback.

Where should I host an AI agent?

Use a managed agent platform for integrated deployment if its portability and controls fit; serverless for short stateless entrypoints and bounded jobs; or containers and Kubernetes for custom workers and control. Hosting is only one layer of the system.

Do production AI agents need Kubernetes?

No. Begin with the least complex platform that meets the requirements. Kubernetes can help with custom worker fleets but does not automatically solve durable state, model quality, permissions or idempotent tool calls.

How do AI agents recover from a crash?

Persist job state and workflow checkpoints outside the worker, redeliver or replay unfinished work, deduplicate by business operation key, and reconcile any external side effects whose result may be unknown.

Can retries guarantee exactly once execution?

No universal end-to-end guarantee follows from retries or a workflow engine alone. For side effects, use transactional boundaries where possible or the target API's idempotency support plus reconciliation.

How do you scale AI agents?

Scale workers using queue age, backlog, throughput and downstream limits; apply bounded concurrency, tenant quotas, model provider rate limits, backoff and admission control rather than scaling pods on CPU alone.

What should a production AI agent deployment checklist include?

A release checklist should specify reproducible build and rollback, data migration safety, task replay, human approval, access permissions, redacted traces, SLOs, disaster recovery, cost limits and independent outcome evaluation.

How much does it cost to deploy an AI agent?

Total cost includes inference, repeated attempts, tool APIs, runtime and queues, storage, monitoring, review and on-call labor. Measure cost per independently accepted business outcome; a model token price alone is not sufficient.
