DIRECT ANSWER

What is GPT-Live-Transcribe?

GPT-Live-Transcribe is an OpenAI API speech-recognition model for live audio. It receives audio in a persistent realtime session and streams incremental text updates, followed by an authoritative final transcript after the client commits the audio turn. The model identifier is gpt-live-transcribe. Unlike a full speech-to-speech assistant, it does not answer with generated speech, execute functions or perform image tasks. Official model specification ↗.

Use it for call captions, accessibility subtitles, live meetings, telephony transcripts, conversation monitoring and streaming voice-input interfaces. Its value is a transcription event stream while speech is happening, not a publicly promised fixed word-error rate or a fixed millisecond response time on every microphone.

OpenAI introduced this model alongside GPT-Transcribe on July 28, 2026. The latter prioritizes accurate file transcription and committed turns, while GPT-Live-Transcribe is tuned for responsive partial captions. The distinction is about when the audio arrives and what metadata your application needs—not simply whether an SDK has a stream option.

MODEL SELECTION

GPT-Live-Transcribe vs GPT-Transcribe vs Realtime Whisper

Start with the audio acquisition pattern. A prerecorded file that produces streaming output need not open a persistent realtime session. The OpenAI transcription guide recommends GPT-Live-Transcribe for continuously arriving sound and GPT-Transcribe for completed audio. Legacy Realtime Whisper is supported in certain integrations but is not the recommended model for a new one.

LIVE INPUT, EARLY TEXT

Choose GPT-Live-Transcribe

You need evolving live captions, partial text for the UI or near-immediate spoken-input feedback. You can handle partial revisions and application-managed turn boundaries.

COMPLETED AUDIO OR DETECTED LANGUAGE

Choose GPT-Transcribe

You already have the recording, or require detected language output or committed-turn processing. You prioritize a different accuracy/cost/latency contract.

IMPLEMENTATION ARCHITECTURE

How does a GPT-Live-Transcribe session work?

01 / CONNECT

Open a transcription WebSocket

Server connects to /v1/realtime?intent=transcription; do not use a conversation-model URL.

02 / CONFIGURE

Select model + audio format

Send session.update with type: transcription, 24kHz PCM example and the model ID.

03 / STREAM

Append speech chunks

Base64-encode PCM16 frames and send input_audio_buffer.append. The server returns transcript deltas as recognition progresses.

04 / COMMIT

Finalize each spoken turn

Client-side VAD or another boundary triggers input_audio_buffer.commit; keep the final transcript keyed by item_id.

OpenAI's guide explicitly says no server_vad or semantic_vad for GPT-Live-Transcribe. Use client-managed turns and budget for jitter, backpressure, resampling, device interruptions and reconnects. If you need browser capture, follow the official WebRTC instructions and never embed a long-lived secret API key into public client-side HTML.

WORKING CONFIGURATION / NO INVENTED FIELDS

GPT-Live-Transcribe WebSocket quickstart (Node.js)

A server-side WebSocket connection uses wss://api.openai.com/v1/realtime?intent=transcription. Importantly, omit model from this connection URL; it belongs in the session.update transcription configuration. This source-aligned example starts a session, prints partial and final text and leaves audio capture to your application's media pipeline.

Terminal · Node.js dependency
npm install ws
Node.js · server-side WebSocket, save as transcribe.mjs
import WebSocket from "ws";

const apiKey = process.env.OPENAI_API_KEY;
if (!apiKey) throw new Error("Set OPENAI_API_KEY");

const ws = new WebSocket(
  "wss://api.openai.com/v1/realtime?intent=transcription",
  { headers: { Authorization: \`Bearer \${apiKey}\` } }
);

ws.on("open", () => {
  ws.send(JSON.stringify({
    type: "session.update",
    session: {
      type: "transcription",
      audio: {
        input: {
          format: { type: "audio/pcm", rate: 24000 },
          transcription: {
            model: "gpt-live-transcribe",
            delay: "low",
            prompt: "A customer support call about an AC-42 subscription.",
            keywords: ["AC-42", "premium plan"],
            languages: ["en", "fr"]
          },
          turn_detection: null
        }
      }
    }
  }));
});

// Audio capture is deliberately omitted. Your pipeline must
// convert incoming audio to base64 PCM16 at 24 kHz.
// ws.send(JSON.stringify({
//   type: "input_audio_buffer.append", audio: base64Pcm16
// }));
// On a client-detected turn boundary, send:
// ws.send(JSON.stringify({type: "input_audio_buffer.commit"}));

ws.on("message", (raw) => {
  const event = JSON.parse(raw.toString());
  if (event.type === "conversation.item.input_audio_transcription.delta") {
    console.log("Partial", event.item_id, event.delta);
  } else if (
    event.type === "conversation.item.input_audio_transcription.completed"
  ) {
    console.log("Final", event.item_id, event.transcript);
  } else if (event.type === "error") {
    console.error(event);
  }
});

ws.on("error", console.error);

What this example does not do: it does not capture the microphone, resample audio, authenticate a browser, reconnect sessions or automatically commit a turn. These are application-specific components that require implementation and testing. Check the maintained OpenAI session and event specification ↗.

TRADEOFFS YOU CAN TEST

GPT-Live-Transcribe latency presets: minimal vs low vs high

Set audio.input.transcription.delay to one of the five documented modes. Lower settings emit partials sooner; higher settings give the recognizer more sound context and can improve recognition quality. OpenAI does not publish a fixed millisecond latency for each setting, so numbers such as “200ms at low” would be invented unless measured on your own deployment.

Qualitative choices from OpenAI realtime transcription guidance
Delay presetPractical starting pointValidation
minimalVery latency-sensitive indicators and assistive interactionMeasure corrections, unfinished partials, early update usefulness
lowLive captioning and fast user-visible updatesMeasure perceived delay and domain-term accuracy
mediumBalance initial readability and transcription stabilityCheck long, noisy and multilingual turns
highWhen complete and accurate words matter more than immediate displayAssess final transcript WER and time to stable text
xhighMaximum tolerated delay for additional acoustic contextMeasure whether extra waiting actually pays off

A useful experiment compares time to first stable caption, time to final transcript, word error rate, named-entity error rate, empty/late turns and correction frequency. Fixed round-trip benchmarks must report microphone, network, audio chunk size, device, background noise and languages. A vendor claim of “low latency” is not a specific SLA.

ACCURACY IMPROVEMENTS

How to use prompt, keywords and languages in realtime transcription

OpenAI supports three hint types: a prompt describing context, a keywords array for literal names and technical words, and a languages array of expected language codes. The model uses them to disambiguate speech. They are hints rather than forced replacements: providing a product name should not cause the recognizer to fabricate it if no one says it.

GOOD CONTEXT

Useful vocabulary

prompt: “Technical support about cloud billing.”
keywords: ["AC-42", "Kubernetes", "premium plan"]
languages: ["en", "fr"]

Prefer short, true terms present in the recording and evaluate names, account numbers and code-switching.

COMMON FAILURE

Overprompting / invalid hints

Do not instruct the model to output a particular transcript. Do not use singular language together with languages. Keywords cannot contain angle brackets or newlines, and unsupported language codes are rejected.

Keep identifiers appropriately redacted and do not embed unnecessary sensitive information in the prompt.

Supported formats include ISO 639-1 such as en, es, fr, selected ISO 639-3 codes and regional Chinese codes such as zh-cn. No “all languages have equal accuracy” claim follows from the support list. Official hint validation rules ↗.

SXF PRACTICAL EVALUATION

Production checklist for live transcription apps

  1. Design turns: manage voice activity on the client or server media layer, send commit deliberately and handle silences or talk-over.
  2. Capture data responsibly: obtain informed recording consent where required, disclose retention and restrict transcript access.
  3. Match your codec: normalize the official PCM16 example to 24kHz; profile packet size, jitter and resampling rather than guessing.
  4. Handle partials vs final: mark tentative captions in the UI and replace by item_id once final transcripts arrive.
  5. Test domain vocabulary: acronyms, contact names, numbers, addresses, dates and bilingual turns; add targeted hints only when relevant.
  6. Protect tokens: keep the OpenAI API key server-side, use secure temporary browser credentials/transport as documented, and rate-limit requests.
  7. Measure comprehensively: WER, entity errors, corrected partial count, initial/stable/final delays, empty and truncated turns.
  8. Fail safely: show connection interruptions, buffered audio loss, quota limits and possible transcript corrections; never show failed speech as confirmed text.

SXF evaluation idea: collect a consented, diverse test set of at least a few dozen real turns; blind the annotators to model identity and sample both easy and hard audio. Compare the five latency presets with identical codec/network, and report confidence intervals for accuracy rather than presenting a single anecdotal demo as performance evidence.

IMPORTANT NON-FEATURES

What GPT-Live-Transcribe cannot do

  • No speaker diarization: the model does not return speaker names or segment speaker labels.
  • No word timestamps or per-word confidence: provide an alternative compatible transcription/alignment workflow when those fields are mandatory.
  • No detected-language output: expected language hints do not mean language detection metadata in the transcript.
  • No native streaming voice response or translation output: speech-to-speech translation uses a separate realtime translation model.
  • No server VAD: manage speech turns in your application and explicitly commit each turn.
  • No fixed advertised 50ms/100ms latency SLA: benchmark delay levels in your own production conditions.
  • No public general-purpose text context token window: do not copy a GPT chat model's context length or hallucinate a maximum transcription word count.
  • Not a free local model: the official distribution is a metered hosted API; do not claim open-weight downloads or laptop quantization.

SEARCH QUESTIONS ANSWERED

GPT-Live-Transcribe frequently asked questions

What is GPT-Live-Transcribe?

OpenAI's live-audio speech-to-text API model that streams partial transcript deltas and a final transcript after each committed turn.

How much does GPT-Live-Transcribe cost?

The published rate is $0.017 per realtime audio minute. An hour of processed audio therefore costs approximately $1.02 before other infrastructure or tool expenses.

Should I use GPT-Live-Transcribe or GPT-Transcribe?

For microphone or call audio arriving now, start with GPT-Live-Transcribe. For a finished audio file or detected-language output, start with GPT-Transcribe.

What WebSocket URL do I use?

Use wss://api.openai.com/v1/realtime?intent=transcription with server-side authorization. Put model gpt-live-transcribe inside session.update, not in the WebSocket URL.

Does it return speaker labels or word timestamps?

No. It does not return speaker diarization, word-level timestamps or confidence scores.

What are minimal, low and high delay settings?

They are qualitative delay/accuracy presets: minimal, low, medium, high and xhigh. No fixed millisecond guarantee is published.

Can I supply keywords and multiple language hints?

Yes. Set prompt, keywords and languages in the transcription configuration. Use a languages array, not the singular language field, and validate codes.

Does it return detected languages?

No. GPT-Transcribe can return them in compatible workflows; GPT-Live-Transcribe uses language hints but does not return detected-language metadata.

How do I know whether a caption is final?

A delta event is tentative. The completed event carries a final transcript; match both by item_id.

Does it support server_vad?

No. For this model, turn_detection should be omitted or null. Your application commits audio turns.

Can GPT-Live-Transcribe produce audio or call functions?

No. It is a speech-to-text model; use a separate voice/chat model for spoken responses or tools.

Are OpenAI's accuracy numbers independently verified here?

No. SXF quotes and labels OpenAI's July 2026 results without claiming to have rerun those evaluations.

Can I use GPT-Live-Transcribe for free?

OpenAI's model card marks the API Free tier as unsupported. This is a paid realtime audio service.

Can I run the weights locally?

No public downloadable self-hosting weights or official VRAM requirement are listed for this hosted model.
