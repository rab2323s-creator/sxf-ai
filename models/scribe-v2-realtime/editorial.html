What is ElevenLabs Scribe v2 Realtime?

Scribe v2 Realtime is ElevenLabs' streaming speech-to-text model for applications that need live transcribed speech instead of waiting for a full audio file. Its documented model_id is scribe_v2_realtime, and its realtime API uses a WebSocket connection. It emits provisional partial_transcript events and stable committed_transcript events.

The primary use cases are live captions, voice-enabled applications, customer support, meeting interfaces and voice agents. Scribe Realtime is speech recognition, not text-to-speech generation and not an LLM with a conventional token context window. The separate Scribe v2 batch model targets prerecorded files; do not conflate its capabilities or pricing with realtime service.

How realtime speech transcription works from microphone to committed text

  1. Capture permitted speech: request microphone consent and isolate appropriate channels. Verify device, codec, sample rate and browser permissions.
  2. Authorize a session: obtain a temporary/single-use session credential using a trusted backend; don't publish your permanent API secret.
  3. Open WebSocket: connect to the documented realtime endpoint with model parameters and the appropriate authorization mechanism.
  4. Send audio chunks: transmit supported encoded audio segments with cadence appropriate to the published SDK and your transport.
  5. Render preview: display partial_transcript as replaceable UI text, never as final audit evidence.
  6. Commit stable segments: append only committed_transcript, preserving order and treating a new segment as distinct.
  7. Handle errors: surface rate limits, disconnections and quota errors; explicitly distinguish “unknown final text” from silence.

Partial transcript vs committed transcript: the most important integration rule

A partial transcript is a provisional hypothesis. It can change as new audio arrives and may repeat or be empty. It is incorrect to simply append every partial to a customer-visible transcript archive. A committed transcript indicates a stable utterance segment for that connection and should be added once. Applications should also avoid firing irreversible tools or final invoices based solely on partial words.

Voice activity detection vs manual commit: how to choose

Realtime transcription commitment modes
StrategyWhat happensBest-fit tests
VAD commitThe system detects a probable speech pause/utterance boundaryLive captions, hands-free input, pauses/noise and interruptions
Manual commitThe client explicitly determines when to commit a segmentPush-to-talk, dictated forms and application-controlled turn completion
Draft/partial textShows interim words quicklyPreview correction rate and perceived latency
Final/committed textStores the utterance after commitEnd-of-turn time, missing trailing words, business actions

VAD responsiveness and chunk size affect user experience. Aggressive endpointing can cut off slow speakers; conservative endpointing may delay completion. Realtime tests should report time to first partial, time to final commit and end-to-end user turn time separately.

Languages, accents and live transcription quality

ElevenLabs markets Scribe v2 Realtime with recognition across more than 90 languages, but that is coverage, not a guarantee of identical accuracy across dialects. Speech conditions also matter: telephony audio, overlapping speakers, multilingual code-switching, keyboard noise, terminology, clipped chunks and poor sample-rate conversion can all degrade the result.

What does ~150 ms realtime latency actually mean?

ElevenLabs advertises a realtime latency figure around 150 milliseconds. That is a provider-stated headline, not an independently established SXF p95, a transcription-completion SLA, or a guarantee for every region and network.

Don't present the 150 ms headline as equivalent to a fully transcribed long sentence or uninterrupted 24/7 uptime. Audio buffering, VAD endpointing, client location and streaming transport can all change practical latency.

How to benchmark real Scribe v2 Realtime before production

  1. Obtain consented, representative audio; avoid collecting sensitive information without a valid basis.
  2. Document language/dialect, microphone device, codec, sample rate, channel and expected speakers.
  3. Establish human-corrected reference transcripts and a fixed normalization process before choosing a vendor.
  4. Run the actual Scribe Realtime WebSocket with supported settings, pinning model and client version.
  5. Record partial/final transcript events, VAD choices, wall-clock timestamps and all error/disconnect classes.
  6. Score final text using WER/CER and domain terms; score interim stability independently.
  7. Measure p50/p95/p99 time to partial and commit, connection setup, interruption handling and concurrency.
  8. Reconcile billable audio with official invoices. Compare batch or competing realtime engines only in matching modes.
  9. Report all failures and confidence limits. Do not declare a winner from selective examples.

Privacy, authentication, retention and production safeguards

Audio streams may contain personally identifiable and confidential information. Protect permanent provider API keys on a backend, authorize browser sessions with short-lived credentials and use WSS rather than cleartext transport. Limit transcript retention, avoid logging raw audio or text indiscriminately and treat partial content as potentially sensitive even when not committed.

Seven common Scribe v2 Realtime integration mistakes

  1. Appending partial transcript events as permanent strings and producing repeated words.
  2. Running an external tool before the utterance is committed and approved.
  3. Using the batch Scribe v2 model ID in a realtime WebSocket request.
  4. Storing permanent ElevenLabs API credentials in a public frontend.
  5. Passing incorrect PCM format/sample rate and blaming the recognizer.
  6. Calling a provider's headline 150ms figure your own measured p95 latency.
  7. Comparing a realtime per-hour price with per-million-token text generation rates.

Scribe v2 Realtime frequently asked questions

What is ElevenLabs Scribe v2 Realtime?

ElevenLabs Scribe v2 Realtime is a streaming speech-to-text service that receives audio over WebSocket and emits provisional and committed transcription events. It is a different product mode from batch Scribe v2.

What is the Scribe v2 Realtime model ID?

The published model ID is scribe_v2_realtime, with the official speech-to-text realtime WebSocket endpoint. Verify request parameters and supported formats in the current API reference.

How much does Scribe v2 Realtime cost?

The official baseline rate checked October 21, 2026 is $0.39 per processed audio hour, equal to $0.0065 per minute before tier adjustments or extras. Confirm the live plan and billing rules before purchase.

How fast is Scribe v2 Realtime?

ElevenLabs advertises latency around 150 milliseconds under its stated conditions. SXF did not independently measure that latency, so this is not a verified p95 production SLA.

Does Scribe v2 Realtime support 90 languages?

ElevenLabs markets Scribe Realtime with support for more than 90 languages. Verify the exact realtime model's current language list and accuracy on your own accents and domain vocabulary.

What is the difference between partial and committed transcripts?

Partial transcripts are provisional text that can be replaced or repeated; committed transcripts are the stable segments an application should append to the saved transcript.

Can I use Scribe v2 Realtime in a browser?

Yes, via the documented browser/client streaming approach, with session authentication. Do not expose a permanent ElevenLabs API key to frontend JavaScript.

Does Scribe v2 Realtime support speaker diarization?

Do not assume realtime provides the same diarization/word timestamps as batch Scribe v2. Check the exact realtime response schema and published feature support.

Is Scribe v2 Realtime better than Deepgram Flux?

A vendor winner requires independent testing on identical consented realtime audio with latency, final WER, stability, error handling and actual invoices. SXF does not claim such a benchmark.

Does SXF test real ElevenLabs streaming?

No. SXF ran an original localhost HTTP synthetic event-consumer test, not the ElevenLabs WebSocket API or actual speech recognition. It demonstrates safe handling of partial and committed events.
