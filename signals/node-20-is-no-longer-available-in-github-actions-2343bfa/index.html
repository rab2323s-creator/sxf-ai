SXF / VERIFIED DEVELOPER CHANGELOG · UPDATED NOVEMBER 8, 2026

On September 23, 2026, GitHub ended Node 20 support as a JavaScript-action runtime and switched Actions execution to Node 24. The temporary ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION opt-out no longer works. Maintainers should release JavaScript actions with runs.using: node24; workflow owners should upgrade incompatible action versions. This is not the same as removing every ability to run Node 20 application code in a job.

IMPORTANT NOVEMBER CLARIFICATION

GitHub's runner team clarified on November 4 that node20 action metadata was being executed using Node 24 and that some runner packages still contained the old binary for compatibility. This is a temporary packaging detail, not supported runtime availability or a reason to keep old actions untested.

SXF TECHNICAL VIEW

The highest-risk migrations are self-hosted or old third-party actions with nonportable dependencies. Audit both the action runtime and the project runtime separately, upgrade supported dependencies, verify the runner and use repeatable acceptance tests before release.

Node 20 is no longer available in GitHub Actions: what to fix and what not to confuse.

Reviewed November 8, 2026

GitHub Actions retired Node 20 as a supported JavaScript-action runtime on September 23, 2026. Runners now execute JavaScript actions with Node 24, and the temporary override ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION=true has expired. If you're searching for “Node 20 is no longer available in GitHub Actions,” “GitHub Actions Node 24 migration” or “runs.using node24,” the first task is to determine whether your problem is in a JavaScript action, a workflow's Node application runtime, or a self-hosted runner. They're related but not identical. This guide explains the change, gives tested-by-source migration patterns, and proposes SXF's own acceptance checklist for avoiding avoidable CI outages. Read GitHub's official retirement notice.

What does “Node 20 is no longer available in GitHub Actions” actually mean?

GitHub's September 23, 2026 changelog states that JavaScript actions now use Node 24 on GitHub Actions runners, and that a temporary opt-out is no longer available. The change applies to github.com and GitHub with Data Residency. If you maintain an action, GitHub recommends changing its metadata runtime from node20 to node24 and publishing a new release. If you consume actions, upgrade to a current release that supports Node 24.

A JavaScript action is a packaged unit such as a checkout, setup or custom repository action. Its action.yml or action.yaml specifies the runtime under runs.using. The runner executes that JavaScript, including any configured pre- and post-job scripts. That is not the same setting as the Node version installed for your repository's npm test or node app.js command.

Was the Node 20 binary physically removed from every runner?

Do not infer that from the announcement's headline. In a November 4, 2026 GitHub runner-team clarification, an engineer said all Actions, including those whose metadata still declared node20, were being run under Node 24. The team had kept a Node 20 binary in runner packages temporarily for compatibility, with removal planned later in November. That packaging detail does not reinstate the supported Node 20 runtime or guarantee an old JavaScript action works unchanged.

It also explains a common source of confusion: an action can still contain runs.using: node20 in its metadata while being executed with Node 24. The actionable question is whether its code and dependencies are Node-24 compatible, not whether the string node20 happens to appear in a repository.

GitHub Actions Node 20 deprecation timeline: 2025–2026

GitHub first described the deprecation on September 19, 2025 and subsequently revised its migration schedule. The official note lists June 16, 2026 as the start of Node 24 by default and September 23 as the cutoff for the temporary Node 20 override. The original article's notices include the date revisions; later comments should not be confused with a new grace period. Official timeline with editor's notes.

Upstream EOL is a security-and-maintenance event; GitHub's September retirement is a specific CI infrastructure policy. They have related motivations but different operational effects.

Does actions/setup-node with node-version: 20 stop working?

Not automatically because of this particular GitHub announcement. The node-version input to actions/setup-node requests a Node executable for the steps in your job. The runs.using setting in the setup action's own metadata determines which Node executable runs the setup action. A Node-24-compatible setup action can, in principle, install another Node release for application scripts, subject to version availability and other constraints. Official actions/setup-node reference.

How to migrate a custom JavaScript GitHub Action from Node 20 to Node 24

If your repository publishes an action, inspect action.yml or action.yaml at its root or within .github/actions/. GitHub's action metadata syntax specifies the runs.using value. A minimal new configuration can be:

action.yml — JavaScript action runtime
name: "My JavaScript action"
description: "Run a checked JavaScript task"
runs:
  using: "node24"
  main: "dist/index.js"

The change is necessary but may not be sufficient. Modernize libraries that depend on older Node internals; confirm whether the action's bundled dist/index.js uses modern ESM or CJS behavior correctly; rebuild committed distribution output; and exercise any declared pre and post hooks. GitHub does not rebuild your committed action bundle just because you edit its metadata.

  1. Find the action declaration. Check root action.yml / action.yaml and custom action directories. Identify Node 20 references in action metadata, not only workflow commands.
  2. Change the runtime. Set runs.using to node24; verify documented main, pre and post file paths.
  3. Update and rebuild. Install supported dependencies and regenerate any checked-in dist/ bundle using the project's build pipeline.
  4. Run a local and CI test. Execute action unit tests and smoke-test the packaged action on a compatible runner; check initialization and post-job cleanup.
  5. Publish a version. Tag and release the updated action, record any breaking changes and update workflows that consume the action.
  6. Observe real runs. Check logs, outputs, network behavior, artifact uploads and expected permissions in the target environment.

Before/after: a safe metadata-only example

Before
runs:
  using: "node20"
  main: "dist/index.js"
After
runs:
  using: "node24"
  main: "dist/index.js"

This is an illustrative syntax change, not a guarantee of binary compatibility. Some old packages, native modules or bundled code require additional changes. The actual test should exercise the same inputs and outputs as production usage.

How to update workflows that consume Node 20-era actions

If your repository uses JavaScript actions, inspect files in .github/workflows/, especially lines beginning uses:. The referenced action may live in another repository, so looking only for node20 inside your own YAML cannot fully audit dependencies. Read each vendor's release notes and action metadata for the pinned version.

Example workflow with Node-24-compatible first-party actions
name: Node 24 smoke test
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: "24"
          cache: "npm"
      - run: npm ci
      - run: npm test
      - run: npm run build --if-present

Important: These v5 references are illustrative known Node-24-compatible releases, not a claim that v5 remains the latest major in November 2026. Both actions/checkout and actions/setup-node document the move to Node 24 in v5, and their repositories document newer majors with additional changes. Select a current, reviewed version suitable for your runner; for sensitive workflows use verified immutable references or GitHub workflow dependency lockfiles where applicable.

This example deliberately uses node-version: "24" because the sample project is also being tested on a supported Node release. If your application still requires 20 temporarily, that is a separate application migration decision from the underlying action's own runtime. Testing applications on Node 24 and testing JavaScript actions under Node 24 should both be part of a complete migration.

How to audit action references quickly

Basic repository searches (not a full dependency audit)
# List referenced actions in workflow YAML
grep -RIn "uses:" .github/workflows/

# Find local JavaScript action runtime declarations
grep -RIn "using:.*node20" .github/actions/ 2>/dev/null || true

# Inspect the job runtime explicitly
node --version
npm --version

The second command only scans local actions under the standard folder. A third-party uses: vendor/action@tag dependency stores its action.yml in the vendor's repository, and a pinned SHA may refer to an older build. GitHub's secure-use reference explains dependency review, immutable pinning and supply-chain controls. Do not automatically update every major version without checking breaking changes.

Node 24 requirements for self-hosted GitHub Actions runners

The migration is especially consequential for self-hosted runners. GitHub's Node-24 migration notice says Node 24 is incompatible with macOS 13.4 and earlier and is not officially supported on ARM32. The September retirement applies to GitHub-hosted and supported self-hosted execution environments, but your team controls the software and OS image on self-hosted machines. GitHub's retirement announcement.

GitHub's official checkout and setup-node READMEs specify Actions Runner v2.327.1 or later for the Node-24-based v5 releases. Newer action features can require still newer runners; for example checkout v6 calls out an additional runner requirement when performing authenticated Git commands from a Docker container action. Do not stop at the minimum version for an earlier major if you choose a newer release.

Why the opt-out is not a rollback plan

Before September 23, GitHub offered ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION=true as a temporary migration escape hatch. GitHub now explicitly says this path is no longer available. Leaving the variable in a workflow can make troubleshooting harder because it implies a fallback that is no longer supported. The correct resolution is to maintain Node-24-compatible actions and supporting runners.

What about a warning that references Node 20?

A warning or outdated metadata does not by itself prove the actual running interpreter is Node 20. Inspect the action's version, runner logs and official compatibility notes. GitHub's November 4 clarification reports that actions declaring Node 20 were still being executed with Node 24. If a failure persists, reproduce it in a minimal workflow and isolate whether it occurs during setup, main execution, post-job cleanup or an application step. Runner-team clarification.

SXF analysis: this is a supply-chain migration, not just a version bump

Our editorial assessment: the biggest risk in the Node 20 retirement is not the text replacement node20 → node24. It is the chain of dependencies behind a CI job. Workflows load actions from different repositories, often pinned to majors or commits. A GitHub-hosted runner can move to Node 24 without every third-party action maintainer having tested the change. At the same time, older self-hosted runner images can make a supported action unusable. Successful migration requires evidence at the workflow, action, runner and application levels.

That gives security teams a second opportunity: audit the trust and permissions of every action while updating it. Check whether the action has access to repository write permissions or production secrets, whether a release tag can be changed, and whether a forked pull request can influence a privileged workflow. GitHub's secure-use guidance recommends dependency lockfiles for verified and transitive action sources, or full-length SHA pinning where lockfiles are not in use. This is an independent concern from Node compatibility, but migration work is an efficient moment to address both.

Frequently asked questions: Node 20 removal from GitHub Actions

When did GitHub Actions stop supporting Node 20 for JavaScript actions?

September 23, 2026. GitHub's final retirement notice says JavaScript actions now run on Node 24 and the temporary opt-out is unavailable.

Does a workflow using node-version: 20 automatically fail?

No. That setup-node input selects a job's application runtime, distinct from the runtime used to run the JavaScript action itself. Node 20 remains end-of-life and should be migrated for security.

What is the action.yml migration?

For a custom JavaScript action, change runs.using to node24, rebuild any bundled JavaScript, test setup/main/post hooks and publish an updated release.

Can I use ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION?

No. GitHub states the temporary override is no longer available after September 23.

Can a GitHub action with runs.using: node20 still execute?

GitHub clarified in November that the runner executes even legacy-declared actions with Node 24. That does not guarantee their code remains compatible or that the Node 20 runtime is supported.

Which checkout and setup-node releases support Node 24?

Both official actions document the move in their v5 majors, with newer majors containing additional updates. Pick a release compatible with your runner and test before rollout.

What is the minimum self-hosted runner version?

For checkout v5 and setup-node v5, GitHub specifies v2.327.1 or later. Other actions and later features may require newer versions.

Which operating systems and architectures are affected?

GitHub says Node 24 is incompatible with macOS 13.4 and older and does not officially support ARM32, so those self-hosted configurations are no longer supported in this change.

Why did GitHub move away from Node 20?

Node 20 reached upstream end of life in March 2026. Maintaining an unsupported runtime increases security and dependency risks; GitHub moved action execution to supported Node 24.

How should a team verify its migration?

Audit all action dependencies and runner platforms, test the packaged action under Node 24, run real workflow smoke tests, inspect logs and protect privileged workflow permissions.
