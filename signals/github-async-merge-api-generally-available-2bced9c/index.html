SXF TECHNICAL EXPLAINER

How GitHub's async merge API works.

Verified October 5, 2026

GitHub's asynchronous merge endpoint changes the integration pattern from “request a merge and wait for the final result” to “submit work, receive a request identifier, then check the result.” That matters most in busy repositories, merge-queue workflows and stacked pull-request systems where a merge can involve checks, rules, retries or multiple dependent pull requests.

01 / SUBMIT

Send the merge request.

Use PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge-async. For a new background request GitHub can return 202 Accepted plus a UUID.

02 / PROCESS

GitHub handles the merge asynchronously.

Background processing lets GitHub retry certain failures and reduces timeout risk for complex merges. The request can merge directly or use a merge queue.

03 / POLL

Fetch the result by UUID.

Poll the result endpoint until the request reports merged, enqueued or failed. An enqueued result means the PR entered the queue; it does not mean the PR has merged yet.

WHY THIS API IS DIFFERENT

Async merge vs the synchronous merge endpoint.

REQUEST CONTROLS

The parameters automation builders need to understand.

merge_action

default, direct_merge, or merge_queue. Default uses a merge queue when the target branch has one configured.

sha

Locks the request to the expected PR head. If the PR changes between request and execution, GitHub cancels the merge rather than merging a different head.

merge_method

For direct merges, the API supports merge, squash, or rebase.

bypass_rules

Can request rule bypass only when the authenticated actor already has permission to bypass those repository rules.

STATUS & FAILURE MODEL

What each response means in production.

200

The PR is already merged or already in a merge queue.

202

The merge request was accepted for background processing; store the returned UUID.

400

The pull request is not ready for merge, such as a closed or draft PR.

409

Another async merge request is already pending; GitHub returns that request's UUID and options.

Important operational detail: branch protection and repository rules are not evaluated during the initial basic-state check. Async merge results are retained for 24 hours after their most recent update, so long-lived automation should persist the outcome it needs rather than treating the result endpoint as permanent storage.

STACKED PULL REQUESTS

Why stacked PR support is the standout capability.

GitHub explicitly documents this as the required merge API for stacked pull requests. When the requested pull request is part of a stack, the operation includes open downstack pull requests. That makes the endpoint materially different for teams and developer tools that organize large changes as dependent, reviewable layers instead of one oversized pull request.

For automation authors, “merge this PR” can represent a graph of dependent changes rather than a single isolated branch operation. Integrations should therefore treat stacked merges as stateful background work and surface the returned status clearly to users.

MIGRATION CHECKLIST

When should an integration move to async merge?

  • Use it for new programmatic merge automation. GitHub now recommends the async API over the synchronous REST endpoint or GraphQL merge mutations.
  • Use it for stacked pull requests. This is the supported merge API for stacked PRs.
  • Model the workflow as a state machine. Persist the UUID, handle pending/merged/enqueued/failed states, and distinguish “queued” from “merged.”
  • Verify permissions. Fine-grained tokens need repository Contents: write for these endpoints.
  • Handle race conditions. Supply the expected head SHA when you need to prevent merging a PR that changed after the request was created.
  • Do not assume result URLs are permanent. The documented result retention window is 24 hours after the latest update.

FAQ

GitHub async merge API questions.

What is the GitHub async merge API?

It is a REST API that requests a pull request merge in the background or adds the pull request to a merge queue. A newly accepted background request can return HTTP 202 and a UUID for result polling.

Does it support stacked pull requests?

Yes. GitHub documents the async merge endpoint as the required API for stacked pull requests, and the operation can include open downstack pull requests.

What permissions does it need?

For fine-grained tokens, GitHub documents Contents repository permission with write access.

How long is the result available?

The result is retained for 24 hours after its most recent update. After that window, requesting the UUID returns 404.
