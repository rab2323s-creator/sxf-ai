Actions Runner Controller 0.15.0: reliability, scale and upgrade changes

Actions Runner Controller 0.15.0 is a Kubernetes-focused reliability and scalability release for GitHub Actions runner scale sets. Instead of adding a new runner model, it changes how ARC upgrades resources, shuts down controllers, re-registers missing scale sets, reports runner state, talks to the Kubernetes API, controls reconciliation concurrency, and cleans up completed ephemeral runners. Those changes matter most to teams operating larger self-hosted runner fleets.

WHAT CHANGED

GitHub’s 0.15.0 release concentrates on controller behavior under scale and during lifecycle transitions. Patch-version upgrades can update runner-set resources in place, controller shutdown timing can be aligned with Kubernetes termination grace periods, and a scale set can be registered again when ARC’s recorded set no longer exists in the Actions service. The controller also shifts several high-frequency operations away from full object updates and status patches, adds configurable Kubernetes client rate limits and reconciliation concurrency, filters more incoming events, and shortens cleanup for successfully exited ephemeral runners.

WHY IT MATTERS

ARC is the Kubernetes-based reference implementation GitHub recommends for autoscaling self-hosted runner scale sets, so controller overhead becomes an operational concern as fleets grow. Version 0.15.0 targets the control-plane work that can create disruption or unnecessary Kubernetes API traffic: upgrades, reconciliation loops, listener request rates, status writes, graceful shutdowns, and runner cleanup. For platform teams, the practical value is a controller that can spend less time rewriting state and more predictably handle large numbers of scale sets without changing how workflows target those runners.

PRICING / CAPABILITY IMPACT

ARC 0.15.0 does not introduce a new GitHub Actions price model. Its impact is operational: fewer disruptive resource replacements during applicable upgrades, smaller Kubernetes API writes, fewer status patches, tunable listener request rates, configurable reconciliation parallelism, and faster deletion of successfully exited ephemeral runners. Those controls can matter when runner capacity is already large enough that API pressure, reconcile throughput, shutdown timing, and stale resource state become part of normal platform operations.

WHO SHOULD CARE

Platform engineering teams operating GitHub Actions on Kubernetes, organizations with many runner scale sets, SRE teams responsible for Kubernetes API health, and developers maintaining internal self-hosted runner platforms should care most. The release is less about visible workflow features and more about reducing control-plane friction as ARC installations become larger, more concurrent, and more sensitive to upgrade and reconciliation behavior.

PRACTICAL TAKEAWAYS

What to do with the information.

Treat 0.15.0 as an operations-focused upgrade: measure upgrade disruption, Kubernetes API request behavior, reconcile latency, listener health, and runner cleanup before and after rollout instead of judging it only by job throughput.

If controller pods sometimes terminate before reconciliation work finishes, review terminationGracePeriodSeconds alongside the controller manager graceful-shutdown timeout so Kubernetes and ARC use compatible shutdown windows.

For large fleets, watch API-server load and ARC metrics before increasing QPS, burst, or max-concurrent-reconciles. Higher concurrency can improve throughput, but it should be tuned against the capacity and rate behavior of the cluster.

WHAT TO VERIFY

Before production use.

  1. Confirm the exact gha-runner-scale-set-controller and gha-runner-scale-set chart versions deployed in each cluster before planning the upgrade.
  2. Review existing terminationGracePeriodSeconds values and controller shutdown settings so graceful shutdown behavior is intentionally aligned after the upgrade.
  3. Capture baseline Kubernetes API request rates, ARC controller metrics, listener metrics, reconciliation latency, and runner cleanup behavior before changing QPS, burst, or concurrency settings.
  4. Test the upgrade on a representative runner scale set and confirm that in-place resource changes do not conflict with custom labels, annotations, sidecars, runner modes, or admission policies used in your cluster.
  5. Verify that logs from controller, listener, and ephemeral runner pods are retained so failures introduced by scale or lifecycle tuning can be diagnosed after pods are replaced.

6 questions
What changed in Actions Runner Controller 0.15.0?

ARC 0.15.0 focuses on reliability and scale: in-place patch-version upgrades, more predictable graceful shutdowns, scale-set re-registration, smaller Kubernetes API writes, metrics-based runner status aggregation, configurable listener rate limits, tunable reconciliation concurrency, event filtering, and faster ephemeral runner cleanup.

Source 1 ↗
Does ARC 0.15.0 reduce disruption during upgrades?

Yes for the upgrade path GitHub describes. Patch-version upgrades can update resources in place, reducing disruption between autoscaling runner sets and ephemeral runner sets compared with replacement-heavy behavior.

Source 1 ↗Source 2 ↗
How does ARC 0.15.0 reduce Kubernetes API load?

The release uses patch requests instead of full update requests for controller changes, moves runner-status aggregation to metrics for key runner-set resources, filters more incoming events, and lets operators configure listener QPS and burst settings.

Source 1 ↗Source 2 ↗
What does max-concurrent-reconciles change in ARC?

The new global and per-controller max-concurrent-reconciles controls let operators tune how many reconciliation loops can execute at the same time. This is primarily a controller-throughput and cluster-load tuning mechanism.

Source 1 ↗
Who should prioritize the ARC 0.15.0 upgrade?

Teams running larger Kubernetes-based GitHub Actions runner fleets should evaluate it first, especially if they experience upgrade disruption, heavy Kubernetes API traffic, reconcile bottlenecks, listener pressure, or slow ephemeral-runner cleanup.

Source 1 ↗Source 2 ↗
Is Actions Runner Controller the supported Kubernetes autoscaling option for GitHub Actions?

GitHub documents Autoscaling Runner Sets in ARC as its supported Kubernetes-based runner autoscaling line and states that only the latest Autoscaling Runner Sets version is supported by GitHub; legacy ARC remains community-supported.
