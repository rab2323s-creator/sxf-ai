TECHNICAL ANALYSIS / 01

Which REST endpoints control GitHub AI Scan for repositories?

GitHub extends the existing AI Scan enablement routes for organizations and repositories. The organization endpoints are GET and PATCH /orgs/{org}/code-scanning/ai-scan, while the repository endpoints are GET and PATCH /repos/{owner}/{repo}/code-scanning/ai-scan. The new repository_scan property can be enabled or disabled, alongside the existing pr_scan setting.

This is a configuration API for authorized administrators, not a scan-execution command. The payload examples in this guide are conceptual field illustrations rather than live tested requests; use GitHub's current REST reference to confirm headers, API version, permissions and supported request bodies before automating production policy changes.

GitHub AI Scan REST API Examples: GET and PATCH repository_scan

Documentation-derived, unexecuted examples. Replace ORG, OWNER and REPO; export an authorized GH_TOKEN. Requests use GitHub API version 2026-03-10. A PATCH modifies configuration only and does not trigger a scan.

Read organization setting

curl -L -sS \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  https://api.github.com/orgs/ORG/code-scanning/ai-scan

Enable organization repository_scan

curl -L -sS -X PATCH \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  https://api.github.com/orgs/ORG/code-scanning/ai-scan \
  -d '{"repository_scan":"enabled"}'

Read repository setting

curl -L -sS \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  https://api.github.com/repos/OWNER/REPO/code-scanning/ai-scan

Disable one repository

curl -L -sS -X PATCH \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  https://api.github.com/repos/OWNER/REPO/code-scanning/ai-scan \
  -d '{"repository_scan":"disabled"}'

HTTP 422 example (illustrative, not captured)

HTTP/2 422
{ "message": "[read GitHub validation details here]" }

A blocked enterprise policy is one documented cause of 422; it is not the only possible validation error. Required permissions: org GET needs owner/security-manager access and fine-grained Administration:read; org PATCH requires Administration:write. Repository GET needs Code scanning alerts:read; PATCH needs Administration:write for the repository and admin access. Classic PAT scopes: org endpoints document admin:org, repo or write:org according to role; repo GET documents security_events (or public-only public_repo), while PATCH documents repo (or public-only public_repo). Confirm the exact endpoint, actor role and entitlement.

TECHNICAL ANALYSIS / 02

What do org inheritance and HTTP 422 mean?

If an organization disables repository scanning, an individual repository under it cannot enable the feature. If the organization enables scanning, repositories inherit that policy but may opt out. Enterprise rules sit above both, and GitHub says a disallowed enablement returns HTTP 422. A batch PATCH that includes pr_scan and repository_scan is atomic when one change is blocked: neither setting changes.

A rollout script should therefore read current effective policy, validate that the enterprise permits the setting, PATCH only intended fields, and read the settings again. Log any 422 as a policy conflict rather than retrying blindly or trying to bypass the enterprise control. An infrastructure-as-code workflow benefits from explicit desired state and a rollback record.

TECHNICAL ANALYSIS / 03

Does turning on AI Scan automatically scan the repository?

No. GitHub explicitly says that enabling AI Scan for repositories does not initiate a scan. Users with write access run repository scans on demand, and each one consumes GitHub Code Security AI credits. A dashboard displaying an enabled toggle is therefore not evidence that a security assessment has happened.

SXF's suggested acceptance test tracks three separate states: policy enabled, scan requested and scan completed with findings reviewed. This avoids conflating administrative configuration, queue processing and human remediation. Budget checks should use the live enterprise credit ledger rather than a fabricated per-run price.

TECHNICAL ANALYSIS / 04

SXF security rollout: what teams should measure

Pilot on a small set of eligible repositories representing different languages, sensitivity levels and maintainer groups. Check the effective organization and enterprise policy first, then enable repository_scan where appropriate. Run an authorized on-demand scan and review findings alongside existing static analysis. Record time to triage, false positives, fixes accepted and credit consumption.

Do not disable established SAST, dependency alerts or secret scanning because an AI feature is enabled. Connect your rollout with the SXF agent-security checklist for authorization boundaries and with the production-agent guide for auditability, retries and rollback. Review every automated finding in source context before changing production code.

POLICY LOGIC / ADMINISTRATOR REFERENCE

The three controls that decide whether AI Scan can run

An effective scan depends on permission at several layers; changing one value is not the same as ordering or completing a scan.

Enterprise policy

If AI Scan is prohibited at enterprise level, an enablement request fails with a 422 response.

Organization and repository

Organization disablement blocks repository enablement. An enabled organization allows repository-level opt-outs.

Scan execution and credits

A user with write access initiates an on-demand scan, which consumes GitHub Code Security AI credits.

These states summarize GitHub's public-preview release announcement; validate current APIs before operational changes. Check the original evidence ↗

READER QUESTIONS

GitHub AI Scan REST API questions

Which property enables AI Scan for repositories?

GitHub documents the repository_scan setting with values enabled or disabled on the organization and repository AI Scan endpoints.

Does enabling repository_scan trigger a full code scan?

No. The setting controls availability. Authorized users must request an actual scan, and the scan consumes AI credits.

What happens when a policy blocks a request?

GitHub describes an HTTP 422 response for disallowed enablement. When a combined pr_scan and repository_scan update is blocked, neither setting changes.

LIMITATIONS

The API is in public preview and its eligibility and billing may change. The announcement does not provide a universal price per scan, an accuracy guarantee or an automatic scan schedule. Enabling AI Scan is not evidence that every repository has been scanned or that all vulnerabilities are identified. The SXF API examples are documentation-derived and not live-tested; HTTP 400 is general troubleshooting, not a documented AI Scan PATCH-specific status. The deployment lab is a proposed checklist, not measured results.
