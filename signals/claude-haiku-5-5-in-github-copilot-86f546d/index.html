When did Claude Haiku 5.5 launch in GitHub Copilot?

October 7, 2026 is the official GitHub Copilot release date. GitHub's changelog says Anthropic's new lightweight model is generally available for supported paid Copilot plans, and describes its main target as fast, high-volume work: subagents, small code edits and terminal tasks. GitHub's October 5 weekly-release roundup, published October 9, repeats the Haiku availability announcement. That recap is a secondary GitHub source, not a different launch date.

The phrase generally available describes the release status. GitHub separately states the rollout is gradual, so a user meeting plan requirements may not see the model immediately. This is not an experimental model-only preview. The original GitHub announcement also reports early testing in which Haiku 5.5 matched Claude Sonnet 5 on many coding tasks while requiring fewer tokens and steps. It does not publish enough details there to infer equal results on all tasks, across all repositories or against Sonnet 5.5. Check the exact GitHub wording.

Is Haiku 5.5 a GitHub model or an Anthropic model?

It is made by Anthropic and offered as a choice inside GitHub Copilot. Anthropic separately released Haiku 5.5 on its own API and Claude products that day. Selecting it within Copilot uses GitHub's supported model integrations, policy layer and billing. It is not the same action as buying an Anthropic API subscription or calling Anthropic's claude-haiku-5-5 model identifier directly. Anthropic's model announcement.

Which GitHub Copilot plans and editors support Haiku 5.5?

GitHub's announcement explicitly lists Copilot Pro, Pro+, Max, Business and Enterprise. Its current supported-model guide confirms plan and client eligibility can change. Copilot Free and Student use auto model selection rather than the same direct manual model picker, so this is not a promise of independently selecting Haiku 5.5 on those plans. Organization restrictions can also override what appears in the model picker. Supported models by plan and client.

How to enable or select Claude Haiku 5.5 in Copilot

For an eligible individual user, start in a supported Copilot client, open a chat or agent session with a model picker, select Claude Haiku 5.5 and give it a bounded coding task. On the GitHub Copilot app, GitHub documents selecting the current model near the prompt box and choosing another available model; a choice may take effect after an active turn finishes. The exact controls differ among VS Code, JetBrains and the CLI. Official Copilot app selection steps.

  1. Check plan: confirm a currently supported Pro, Pro+, Max, Business or Enterprise seat.
  2. Check client: update or open the Copilot interface listed by GitHub and locate its model picker.
  3. For work accounts: check whether an organization or enterprise policy permits this Anthropic model.
  4. Select Haiku 5.5: use the named model rather than assuming an Auto/Fusion route will pick it.
  5. Start with a testable request: for example, improve one function and run its existing unit tests in an authorized workspace.
  6. Review cost and output: assess the patch, failures and AI-credit consumption before making it a team default.

What if Haiku 5.5 is missing from the model picker?

First check the current GitHub model list. Then confirm your plan, supported client, software version and gradual rollout status. For Copilot Business and Enterprise, admins can configure model access in GitHub Copilot settings. GitHub's model access guide explains that policy controls can prevent a model from appearing even if the member has a seat.

How do organization admins manage it?

GitHub's docs describe an organization owner's path through Organization Settings → Copilot → Models. When delegated by enterprise policy, a model may be marked Enabled, Disabled or inherit a Default availability setting. An enforced enterprise policy cannot be overridden at the organization level. Best Claude Haiku 5.5 use cases in GitHub Copilot

The model's advantage is not that it makes expensive engineering judgment unnecessary. It is positioned for small, well-defined steps that occur often. The examples below combine GitHub's stated focus with SXF's recommended acceptance checks; they are proposed uses, not firsthand benchmark results.

01 / QUICK EDIT

Small code changes

Rename a function, update validation logic or refactor a small module with explicit expected behavior. Accept only a reviewed diff with relevant passing tests.

02 / TERMINAL HELP

Command explanations and narrow fixes

Ask for a concise explanation of a test failure or command. Inspect any suggested shell action before running it, especially destructive commands.

03 / SUBAGENTS

Focused delegated work

Let a stronger planner delegate log summarization, file lookup or documentation synthesis while retaining architecture and final integration decisions.

04 / REPEATED WORK

Documentation and triage

Produce change summaries, classify straightforward issues or update structured documentation under a clear schema and validation rules.

GitHub's official model comparison recommends Haiku 5.5 for quick, reliable responses to lightweight coding questions. Anthropic separately highlights classification, summarization, compaction and browser-oriented tasks; those are capabilities of the base model, not a guarantee that every Anthropic API feature is exposed identically inside every Copilot client. For agent context see SXF's agentic AI guide.

Example prompt for a focused Copilot task

Original SXF sample: “In src/formatDate.ts, fix the empty-input behavior without changing valid date formatting. Reproduce with a failing unit test, update only the function and its test file, run the relevant tests, and report the diff plus any unverified cases. Do not modify dependencies or deployment settings.”

This prompt is deliberately narrow. It defines the permitted files, the test, and the evidence expected on completion. A model that merely explains a change without producing or validating it should not be counted as a successful coding agent run.

Claude Haiku 5.5 GitHub Copilot pricing and AI Credits explained

GitHub moved Copilot model interactions to per-token usage-based billing: input, output, cached-input reads and cache writes can contribute to the price. Usage converts to GitHub AI Credits, where 1 credit = $0.01 USD. Included credit allowances vary by Copilot plan, and overages depend on budget controls and billing settings. These facts come from GitHub's current Models and pricing documentation, not an estimate by SXF.

Worked example: what would a short Copilot task cost?

For an illustrative task using 20,000 uncached input tokens and 2,000 output tokens, with no cache writes, retries or extra tool charges, the listed rate calculation is: input $0.002 (0.02 million × $0.10), plus output $0.001 (0.002 million × $0.50), or $0.003 total. At GitHub's conversion, that is 0.3 AI Credits. This is pure token arithmetic, not a measured Copilot session bill or a guarantee of how many requests a subscription includes.

For a prompt over 100K input tokens, rates change substantially. Before sending huge contexts to a lightweight model, ask whether a smaller relevant file selection, a task-specific summary or a better retrieval strategy could reduce cost and improve relevance. See SXF's AI model cost calculator and model pricing directory for broader comparisons; verify any platform-specific fees directly in GitHub.

Are inline code completions billed the same way?

No. GitHub's billing page says code completions and next-edit suggestions are not billed in AI Credits and remain unlimited for paid Copilot plans under their existing counting method. That distinction does not turn model-selected chat and agent work into unlimited usage; it prevents confusing different product surfaces. Enterprise administrators can set AI-credit budgets to limit surprise spending.

SXF original analysis: when should a coding team route work to Haiku 5.5?

Our interpretation: GitHub's Haiku integration is an architectural opportunity as much as a new entry in a model list. Teams can use a powerful model as an accountable planner and a cheaper model for small repeated subtasks. Yet every handoff creates another potential error: selecting the wrong file, misreading context, producing untested code or losing the goal. A routing system must verify outputs instead of assuming that a lower unit rate translates into lower engineering cost.

GATE 01 / SCOPE

Is the task bounded?

Use clear files, inputs, output schemas and permissions. Ambiguous architecture work should escalate rather than silently expand the subagent's authority.

GATE 02 / CORRECTNESS

Did tests really pass?

Demand a reproducible test and a reviewed diff. Count fully accepted patches, not model-generated patches alone.

GATE 03 / LATENCY

Was the full task quicker?

Measure time to accepted change, including re-prompts, failed tool calls, switching models and reviewer effort.

GATE 04 / BILLING

What was the total spend?

Use Copilot credits across all calls. Long context and retries can erase much of the savings from cheap prompts.

GATE 05 / SAFETY

Could the agent exceed its role?

Check permissions, untrusted repository instructions, secret protection and human approval of high-impact edits.

GATE 06 / ESCALATION

When must stronger models take over?

Set triggers for uncertain requirements, repeated failed tests, security-sensitive code or broad cross-module changes.

An SXF pilot study that can actually test the trade-off

A practical starting experiment is 30 task attempts distributed among documentation changes, focused bug fixes, unit-test improvements, data extraction and moderate cross-file work. Compare Haiku 5.5 and Sonnet 5.5 using fixed starting repository snapshots, the same permissions and prewritten acceptance tests. Log the failed attempts as well as successful ones. For high-risk tasks, include a senior reviewer who does not know which model produced the patch. This is a proposed SXF methodology, not an experiment conducted for this article.

Measure accepted-task rate, median and p95 time, credits consumed, human review minutes, failure severity and regression rate. The winning model is not the one that generates the most code. It is the one delivering the best risk-adjusted number of accepted results at a price the team can sustain.

A useful escalation rule

Begin with Haiku for a narrow change. Escalate to Sonnet when a unit test fails repeatedly for nontrivial reasons, the change spans several architectural layers, or the model cannot justify an assumption using code evidence. Try Opus for genuinely complex and high-risk work where the incremental reasoning value has already proved useful in your test set. The named thresholds should be defined by each team's data; SXF does not claim that these are GitHub's or Anthropic's internal routing rules.

GitHub's later Copilot Fusion routing news provides separate context on managed model orchestration. Do not assume enabling Haiku alone activates Fusion or that the two experiences select identical underlying models. For safe automated edits see AI Agent Security and AI Agent Reliability.

Privacy, model policies and security for business Copilot teams

Choosing Haiku 5.5 should not be treated as permission to expose secrets or grant broad filesystem and network access. A capable model can still follow malicious instructions embedded in issue text or repository files, propose destructive commands or introduce incorrect dependencies. Restrict agent permissions and validate changes at the same standard as human-written code. GitHub's organization model controls are one layer of governance, not a complete security evaluation.

Business teams should review provider-hosting and data-handling documentation, enterprise policies, agent sandboxing, repository permissions and logging. The GitHub release does not constitute an independent audit of every organization using the model, nor does Anthropic's system card prove the absence of coding errors. Before broad adoption, decide which datasets are allowed in prompts and which tool actions need explicit human approval.

Frequently asked questions about Claude Haiku 5.5 and Copilot

Is Claude Haiku 5.5 available in GitHub Copilot?

Yes. It reached general availability on October 7, 2026 for named Copilot plans, with a gradual rollout across clients.

Which plans can select Haiku 5.5?

GitHub names Pro, Pro+, Max, Business and Enterprise. Free and Student plans rely on auto selection rather than equivalent direct model choice.

Can I use it in VS Code, Copilot CLI and JetBrains?

Yes, GitHub explicitly lists those clients, together with Visual Studio, Xcode, Eclipse, cloud agent, Copilot app, github.com and Mobile.

Why is it not appearing in my model picker?

Check the gradual rollout, plan, supported client and administrator policy. Use GitHub's current supported-model documentation.

Is Haiku 5.5 cheaper than Sonnet 5.5?

Its published per-token rates are lower for default prompts. Actual cost per accepted task depends on context size, output, caching, retries and human review.

What does it cost in Copilot AI Credits?

For inputs up to 100K tokens GitHub lists $0.10 per million input and $0.50 output, plus cache-specific rates. One AI Credit equals $0.01; subscription allowances and additional spend vary.

Are requests longer than 100K tokens priced differently?

Yes. GitHub lists a more expensive long-context tier above 100K input tokens; check the live pricing table before budgeting.

Is Haiku 5.5 as capable as Sonnet 5.5 for agentic coding?

Not across the board. Anthropic reports stronger Sonnet 5.5 performance on Terminal-Bench 4.0; Haiku targets faster, narrower tasks.

Can administrators restrict this model?

Yes. Organization and enterprise owners can enable or disable supported Copilot models according to delegated or enforced policies.

What should a development team test first?

Start with test-covered small edits and compare accepted output, review burden, latency and credits with a stronger-model baseline.
