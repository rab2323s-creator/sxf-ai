GitHub repository security advisory comments API: public preview

GitHub’s repository security advisory comments API brings advisory discussion into the REST API for the first time. Security teams can now list, retrieve, add, and edit non-confidential comments on repository security advisories, including advisories created from private vulnerability reports. The change matters because triage context, coordination notes, audit evidence, and migration data no longer have to remain locked inside the web interface.

SOURCEGitHub
PUBLISHEDOctober 2, 2026
REVIEWED2026-10-04
STATUSPublished

WHAT CHANGED

Before this public preview, repository security advisory discussion was available through GitHub’s web interface but not exposed through a comparable REST comments workflow. GitHub now provides REST operations to list advisory comments, fetch an individual comment, add a comment, and edit an existing comment. List operations can be limited to comments updated since a given time, and repository advisory responses now expose a comments count. GitHub also adds the linked repository-advisory comment count to global advisory responses so tools can detect active discussion before fetching comment bodies.

WHY IT MATTERS

Repository security advisories often contain the operational context that does not fit neatly into CVE metadata: questions from reporters, triage decisions, reproduction details, coordination status, and follow-up notes. REST access means that context can participate in the same automation patterns teams already use around issues and pull requests. Security engineering teams can export discussions for audits or migrations, add triage notes from internal tooling, identify advisories with active discussion, and build workflows around private vulnerability reports without requiring a person to copy information out of the GitHub web UI.

PRICING / CAPABILITY IMPACT

This release changes workflow capability rather than pricing. Security tooling can now treat repository-advisory discussion as structured API data instead of browser-only context. That enables incremental synchronization, audit exports, migration tooling, automated triage notes, and advisory dashboards that first inspect comment counts before fetching discussion content. The main boundary is confidentiality: REST exposes non-confidential discussion only, while confidential maintainer comments remain outside this REST surface.

WHO SHOULD CARE

Application security teams, open-source maintainers, vulnerability-management platform builders, security operations teams, auditors, and organizations migrating advisory data should care most. The API is especially useful when repository security advisories are part of a larger security workflow and the discussion itself contains triage context that must be synchronized, analyzed, archived, or updated by internal tooling.

PRACTICAL TAKEAWAYS

What to do with the information.

Use the comments count as a cheap discovery signal before fetching discussion bodies when building organization-wide advisory dashboards or migration tooling.

Source 1 ↗

For audit or archival pipelines, synchronize comments incrementally with the updated-since filter and store advisory identifiers alongside comment records so the discussion remains traceable to its source advisory.

Source 1 ↗

Do not assume REST exports contain every maintainer discussion. If confidential comments are in use, design the audit process around the fact that those comments are intentionally omitted from the REST endpoints.

Source 1 ↗Source 2 ↗

Separate read-only integrations from tools that add or edit triage notes, and grant only the repository security advisories permission level required for the workflow.

Source 1 ↗Source 2 ↗Source 3 ↗

If a workflow depends on deleting comments or changing a comment between regular and confidential, account for current limitations: REST deletion is not supported, and GitHub does not let a posted comment switch confidentiality state.

WHAT TO VERIFY

Before production use.

  1. Confirm that the target repository and plan are covered by the current public-preview rollout before depending on the comments endpoints in production automation.
  2. Verify the exact repository security advisories read or write permission required by the token or GitHub App for each operation your integration performs.
  3. Treat the advisory comment count as a count of non-confidential discussion, not a guarantee that every maintainer-only note is represented.
  4. If the workflow handles private vulnerability reports, test access using the same reporter, collaborator, maintainer, and app permission roles that will exist in production.
  5. Design around the current no-delete limitation for REST comments and decide how your system will handle corrections that cannot be represented as deletion.

FAQ

6 questions
What can the GitHub repository security advisory comments API do?

In public preview, the REST API can list comments on a repository security advisory, get a single comment, add a comment, and edit a comment. GitHub also supports filtering listed comments by update time.

Source 1 ↗
Does the comments API work with private vulnerability reports?

Yes. GitHub says the REST comments endpoints work with repository security advisories created from private vulnerability reports, subject to the same access rules that control the advisory itself.

Source 1 ↗Source 2 ↗Source 3 ↗
Can the REST API return confidential advisory comments?

No. GitHub states that confidential comments are not returned by the new REST comments endpoints. Confidential comments are maintainer-only, require repository write access, and are available separately through GraphQL.

Source 1 ↗Source 2 ↗Source 3 ↗
What permissions are required for security advisory comments?

A caller must be able to view the repository security advisory and have the appropriate repository security advisories read or write permission or token scope for the operation. Users who cannot access the advisory cannot access its comments.

Source 1 ↗Source 2 ↗Source 3 ↗
Can repository security advisory comments be deleted through the REST API?

Not in the current public preview. GitHub supports listing, reading, adding, and editing comments through these REST endpoints, but deleting comments is not yet supported.

Source 1 ↗
Which GitHub plans have the advisory comments API preview?

GitHub says the public preview is available for public repositories on GitHub Free, GitHub Pro, GitHub Team, and GitHub Enterprise Cloud.
